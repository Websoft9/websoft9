# Websoft9 AI 助手方案：基于 Pydantic AI

日期：2026-10-21

状态：目标设计，尚未实施。本文不表示模型、工具、会话或确认功能已经交付。

## 1. 目标与决策

为 Websoft9 提供“有引导、懂当前应用、能实际检查”的运维助手，而不是向用户开放一个通用编程终端。

采用 **Console 原生交互 + AppHub 内嵌 Pydantic AI + 受控平台工具**。不引入第三方原生工作区作为最终 AI 助手界面，也不引入 Docker Gordon 产品；参考 Gordon 的上下文入口与操作确认体验。

本文明确 AI 底座、用户体验、对象和目录边界及迁移方式；应用能力分类和业务保护规则继续以 [AI 集成架构](ai-integration-architecture.md) 为准，CLI 的现状与实现约定见 [CLI 整体规划](cli-implementation-design.md)。底座与正式 Console 接入方式以本文为准。

| 决策 | 采用方式 | 不做什么 |
| --- | --- | --- |
| Agent 底座 | Pydantic AI，按需安装模型依赖，初期一个 Agent | 自研推理循环、多 Agent 调度、完整 Coding Harness |
| 后端 | 集成现有 Python AppHub | 新建 AI 微服务、公开端口或独立认证系统 |
| 前端 | 沿用 React、MUI、平台语言和主题 | 新建站点、强制引入 Next.js、修改上游第三方 UI |
| 执行 | 具体工具适配已有 Service 或已准入 CLI | 任意 Shell、任意 Docker API、任意 SQL |
| 任务 | 复用已有业务任务和跟踪标识 | 另造安装、备份和应用状态系统 |
| 知识 | 平台规则常驻，任务 SOP 按需加载 | 全量手册塞进提示词、依赖自动扫描用户目录 |
| 部署 | 现有镜像和网关承载，依赖随镜像发布 | 首次访问在线安装依赖、默认部署本地模型服务 |

Pydantic AI 是 Python Agent 库，不是安装后即有完整 UI 的产品。它承担模型交互、类型化工具和事件能力；产品界面、会话归属、授权、确认和持久化由 Websoft9 补齐。框架版本与实际依赖在实施时锁定，本文不以未经兼容检查的版本号作为交付承诺。

## 2. 整体架构与影响

```text
Console：场景入口 / 应用内入口 / 对话与结果
                         |
AppHub：认证、会话归属、目标绑定、确认、事件输出
                         |
Pydantic AI：模型交互、补充提问、选择受控工具
                         |
工具适配：参数校验、范围检查、脱敏、执行前置条件
                         |
现有 Service 或受控 CLI → 应用 / Gitea / Portainer / NPM / Restic
                         |
现有任务进度与实际状态 → 验证 → Console
```

### 2.1 职责边界

| 层 | 负责 | 不负责 |
| --- | --- | --- |
| Console | 目标可见、场景选择、对话、证据、确认和进度 | 保存模型密钥、判断用户是否有权执行 |
| AppHub AI 接入 | 身份、会话、目标、批准及运行预算 | 复制应用状态机、绕过现有业务校验 |
| Pydantic AI | 理解问题、组织工具调用、结构化反馈 | 自行扩大目标或权限、授予操作批准 |
| 受控工具 | 校验参数与范围、调用业务、输出脱敏证据 | 接收并执行模型生成的任意命令 |
| Service / CLI | 实际业务操作、资源与冲突检查 | 仅凭模型文字认定用户已确认 |

底座替换对部署结构影响较小，对产品开发影响中等：新增 AI 配置、会话及批准状态、对话界面和工具适配。既有应用执行器、配置仓库、备份和业务任务保持不变，不能将此描述为简单替换一个依赖包。

现有 CLI 继续面向人工、脚本和 Agent 使用。工具可直接复用合适的 Service；需利用 CLI 契约时，由服务端构造固定命令与参数列表，不通过 Shell 拼接模型输出。不为同时支持两条调用路径而重复业务实现。

## 3. 用户体验

### 3.1 模型配置与首次使用

管理员在平台设置中配置模型供应商、受支持的 API 类型、接口地址、密钥和默认模型。首期只提供一个默认模型，不引入多模型自动路由。

- 未配置：显示“AI 助手尚未配置”，有权限者进入设置；其他用户联系管理员。
- 配置错误：区分连接失败、认证失败、模型不支持所需工具等情况，不假装助手可用。
- 已就绪：显示当前模型和数据使用提示，用户无需添加项目或选择文件目录。
- 密钥只在服务端保存，前端仅见脱敏状态；不进入消息、工具结果或日志。
- 沿用平台配置和秘密管理约定；现有机制不足时在 AI 配置范围内补齐，不建立独立通用密钥平台。
- 使用外部模型会发送问题和必要的脱敏诊断材料。自托管 Agent 不等于数据不出服务器。
- 自定义模型端点仅管理员可配置，校验协议、TLS 和允许的目标；不能由对话临时指定模型请求地址。

配置变化只影响后续运行，不在进行中的一次运行内静默切换模型；不承诺所有 OpenAI-compatible 接口都支持相同工具或流式协议。

### 3.2 三类入口

| 入口 | 交互 |
| --- | --- |
| 全局“AI助手” | 场景卡片、自由输入、最近会话；缺少目标时从平台应用列表选择 |
| 应用详情 | “AI 排查”携带当前应用标识进入，不再要求提供容器名 |
| 安装失败或任务页 | 携带实际任务标识、应用标识和失败阶段，避免用户复制全量日志 |

场景分类包括应用打不开、部署应用、运行巡检、域名 HTTPS、备份恢复和磁盘空间。入口由已开放能力决定；未实现的操作明确标为未开放，不提供会误导用户的执行按钮。

### 3.3 对话闭环

遵循“场景入口 → 带入对象 → 引导补充信息 → 调用工具 → 展示证据和方案 → 确认操作 → 验证结果”。

这不是固定七页向导：已知目标不重复询问，信息足够就开始只读检查，纯咨询不访问服务器。选项和自由输入共存；选项必须映射到平台认可的值，不把模型输出直接当作可执行 UI 指令。

会话顶部持续显示目标应用和模式。页面导航不自动改变旧会话目标；显式更换目标后使旧待执行操作失效。部署新应用的目标是模板与部署计划，不伪造尚不存在的应用标识；执行后使用平台返回的真实标识。

展示的是操作进度而非模型内部推理，例如“读取应用状态”“查看近期日志”“核对反代目标”。

### 3.4 证据、方案和结果

每项证据包含实际来源、目标、采集时间、摘要和截断或缺失标记，可跳转既有平台页面。事实与推测分开；未读取到日志不等于没有错误。

建议方案展示具体目标、动作、参数差异、服务中断风险和后续检查。用户可以继续检查、确认、拒绝或退出。只读阶段只能提出方案，不能出现可执行修复按钮。

结果区区分“未执行、已提交、进行中、已完成、失败、结果未知”。命令退出成功不能代替应用健康检查；连接中断后重新读取实际状态，不猜测成功，也不自动重做写操作。

## 4. 场景示例：应用打不开

```text
用户在 WordPress 详情点击“AI 排查”
  → 顶部显示当前应用，只读模式
  → 必要时选择症状：502/503、连接超时、证书错误、不清楚
  → 检查实例、关联容器、近期日志、端口和反代目标
  → 展示证据、可能原因、缺失信息与建议
  → 首期：引导到对应人工操作页面
  → 后续：获准开放的具体修复，用户确认后执行并复查
```

诊断范围由当时已接入的工具决定。未实现证书或网络检查时明确列出缺失项，不宣称已全面检查。对外访问检查只使用平台解析的目标与允许的网络范围，不提供任意 URL 抓取能力。

首次任务不能默认重启、清理、重装或修改主机；诊断中的 137、502、超时等现象须结合实际证据解释，不能仅凭错误码决定修复动作。

## 5. 工具、对象与执行边界

### 5.1 服务端任务上下文

后端保存登录用户、会话所有者、任务类型、允许的目标集合、可用工具、关联任务及待确认操作。通过 Pydantic AI 的运行依赖传入工具所需上下文；身份和权限不由模型参数决定。

- 当前应用由后端解析其容器、卷、配置仓库和反代关系，不能仅按名称推断。
- 读取关联资源也检查范围，共享资源只返回本任务所需信息。
- 全局查询仅开放必要的脱敏应用摘要；跨应用检查先明确目标集合。
- 应用范围只是任务约束，不自动赋予用户本来没有的权限。
- 复用当前真实的身份与权限机制；首期面向可信管理员，不宣称已经实现租户隔离。
- 未初始化、未登录或会话失效时拒绝 AI 访问；关闭平台登录要求不等于允许匿名调用模型和工具。
- 所有消息、事件订阅、历史读取、产物下载和确认操作均检查会话归属。

### 5.2 最小工具集合

下表为能力设计，不是已经发布的函数名：

| 类别 | 工具能力 | 开放方式 |
| --- | --- | --- |
| 目标识别 | 查找应用、读取应用详情 | 脱敏摘要，绑定允许目标 |
| 诊断 | 关联容器状态与日志、相关任务状态、访问配置摘要 | 已确认无业务写入的只读调用 |
| 预检 | 模板信息、端口检查、编排校验 | 按成熟度开放，不自动安装 |
| 变更 | 具体应用启停、配置更新等 | 单项准入，批准后执行 |
| 高风险 | 覆盖恢复、删除资源等 | 不作为首期能力，满足业务前提后另行开放 |

不提供任意 Shell、通用容器 Exec、通用 SQL、任意文件路径、明文凭证读取或无范围的外部网络工具。未注册工具默认不可用；不能借自定义任务、预设命令、SSH 授权准备等入口间接绕过。

### 5.3 批准与幂等

Pydantic AI 的延迟工具能力用于暂停和恢复；批准是否合法仍由 AppHub 决定，不创建独立审批服务。

服务端待确认记录绑定用户、会话、操作、目标、规范化参数、必要的资源版本、有效期和消费状态。确认请求只引用服务器记录，不接受前端重新提交任意操作参数。

执行前重新检查登录态、权限、资源状态和冲突条件；目标或方案变化必须重新确认。拒绝、过期或模型声称“用户同意”均不构成批准。跨站写请求沿用或补齐平台的 CSRF/Origin 防护。

并发确认通过持久化状态的原子转换避免重复消费。已提交任务记录实际跟踪标识；崩溃或网络中断后先查询状态，不能在结果不明时自动重试写操作。这是 AI 会话的批准与关联数据，不另建业务任务状态机。

## 6. 知识、工作目录与数据

### 6.1 平台知识

常驻规则描述应用语义、配置真源、秘密保护和禁用行为；八个任务 Skill 复用现有规划，按实际开放能力加载。

Pydantic AI 不被假定会自动发现项目的 `AGENTS.md` 或 Skills。由 AppHub 明确加载随版本发布、只读的规则和 SOP，复用文档内容而非依赖某一 Coding Agent 的目录扫描约定。应用仓库中的指令不能覆盖平台规则。

日志、配置、应用内容与外部文档都是不可信输入，不能把其中的指令提升为系统规则。规则与 Skills 指导流程，不承担授权。

### 6.2 业务对象不等于工作目录

应用标识及资源关系是业务目标；模型所见是按需筛选的证据；进程当前目录只是文件行为的默认位置。诊断通过工具查询 Service，通常不需要给 Agent 应用目录。

如需报告或配置草稿，按需创建会话工作区。目录是建议布局，实施时接入真实的数据根解析，不引入新的部署参数：

```text
<DATA_ROOT>/ai/
  sessions/                 # 私有会话与批准数据，模型不可直接读写
  workspaces/<opaque-id>/   # 会话临时报告与脱敏材料
```

由服务端创建不透明标识并检查所有者、配额和保留期限，不接受模型或用户指定绝对工作目录。普通诊断不强制创建工作区，不为每个应用启动常驻 Agent 或容器。

| 资源 | 访问约束 |
| --- | --- |
| Gitea 配置 | 通过正式仓库接口，修改有差异、SHA 检查和批准 |
| 应用数据卷 | 需要时经受限文件工具，核对真实路径、符号链接与归属 |
| 应用日志 | 工具读取、限量并脱敏，不挂载全量主机日志供模型浏览 |
| 工作区草稿 | 临时产物，不是应用配置真源，不直接触发发布 |
| 平台密钥、Docker Socket、主机根目录 | 不向 Agent 暴露通用文件或终端能力 |

工作目录不是沙箱。AppHub 本身的权限也不意味着模型可以使用其全部能力；需要执行模型生成的任意代码时，应另做隔离设计，不纳入本方案。

### 6.3 会话与留存

至少保存会话所有者与目标、必要的消息历史、工具证据摘要、待确认记录和业务任务引用。复用平台持久化方式，不在本文预先固定表数量或外部数据库。

历史与证据均经过脱敏和限量；不永久存储全量日志。用户可删除自己的会话，后台按配置清理到期临时产物。删除会话不删除已有应用或业务任务。刷新、重启及断线后的待确认状态必须可恢复或明确失效，不依赖内存中的等待回调。

## 7. 前端与运行集成

复用基础消息组件与成熟流式客户端，使用 MUI 实现平台专属的场景、目标、证据、确认和结果卡片。Pydantic AI 支持的 UI 事件适配可以减少协议工作，但不是现成的完整网站。

优先评估 Vercel AI Data Stream 与现有 React 的适配；它不要求 Vercel 云部署或 Next.js。若满足不了工具批准和自定义进度，只补充必要的平台事件，不同时维护多套前端协议。具体客户端与依赖版本实施时确定。

AppHub 在现有认证路由体系内提供 AI 请求与流式响应，不新增公开端口或独立网关。前端只提交会话和用户输入；历史、身份和批准状态以服务端为准，不能信任浏览器伪造的工具结果。

事件需表达文本、补充提问、工具进度、证据、待确认操作、业务任务状态和错误。隐藏内部推理及秘密，不透传 SDK 内部对象作为长期前端契约。

限制模型请求时长、工具次数、并发、输出量和消耗；初期使用集中默认值，不先建设复杂计费系统。重复失败或达到预算时明确结束并保留证据。SDK 重试不能导致业务写入重复，失败不能返回成功形状的默认值。

取消等待模型不等于取消已提交业务任务，停止操作不能自动回滚已发生变更。UI 必须显示当前实际任务状态和可用的人工处理入口。

关闭不必要的 SDK 云端追踪，不默认上报对话和工具内容。沿用平台日志并脱敏，避免为 AI 额外引入强依赖的观测服务。

## 8. 与既有实现的衔接

产品当前不提供 AI 助手入口，Console 菜单、AppHub 接口、Supervisor 服务、网关规则和镜像安装中的原有 AI 工作区实现已全部移除，因此不存在新老两套入口并存的问题。

1. 新一轮实施直接从原生助手开始，不再恢复旧的嵌入式原生工作区。
2. 新助手入口放在“数据库”之前，沿用平台主题和语言。
3. 未使用的旧路由必须保持关闭，不能遗留绕过新工具边界的终端入口。

整个实施不新增安装端口、域名或跨域 SSO。

## 9. 分阶段交付与后续验收

本轮仅编写设计，以下是未来实施与验收要求，不表示已经执行。

| 阶段 | 交付 | 完成标准 |
| --- | --- | --- |
| A：配置与原生只读闭环 | 模型配置、会话、场景入口、应用绑定、诊断工具和证据 | 用户不需要理解项目目录，能完成“应用打不开”的有证据诊断 |
| B：预检与受控写入 | 部署预检、具体写工具、批准恢复和任务展示 | 拒绝不执行、并发不重复执行、冲突重新确认、实际结果可查 |
| C：替换与扩展 | 接入原生助手菜单，逐项开放其他技能 | 原有业务不变，旧旁路关闭、历史数据不误删，不宣称所有规划能力已开放 |

未来需覆盖：未配置及错误配置；首次使用；中英文与明暗模式；对象切换与跨范围拒绝；秘密脱敏；恶意日志指令；批准过期、拒绝、重复和重启恢复；任务超时与结果未知；页面刷新、断线和预算耗尽；Gitea SHA 冲突；现有业务回归。

不以聊天演示代替工具授权、业务保护或成功率验证；也不把“所有问题都能修复”作为产品承诺。
