# Websoft9 AI 助手：功能需求与方案

日期：2026-10-21
状态：目标设计，尚未实施。本文不代表任何能力已经交付。

## 1. 产品定义

**把“用户自己找功能、查资料、分析故障、组织操作”变成“用户说明目标，平台引导并协助完成”。**

它不是给平台增加一个聊天窗口，而是降低应用管理与运维门槛的统一任务入口。菜单继续存在，但用户不必先学会菜单：说出目标即可进入对应的流程，平台负责取证、解释、组织步骤、在获准范围内执行，并确认结果。

三段价值，对应三类用户困境：

| 困境 | 助手提供 |
| --- | --- |
| 不知道从哪里开始 | 目标即入口：把“部署应用 / 应用打不开 / 绑定域名 / 备份恢复 / 磁盘空间 / 平台异常”变成可点可选的目标，而不是要求用户选菜单 |
| 不知道该检查什么、看不懂 | 先定位到层与对象，再自动收集该层证据；用易懂语言解释事实、原因与下一步 |
| 操作繁琐、担心出错、不知是否解决 | 组织成可执行步骤并说明影响，确认后执行，执行后核对真实状态 |

**成功标准不是“回答得像不像 AI”，而是**：更容易开始、更快找到原因、更少出错、清楚知道是否完成。

## 2. 使用者与运行环境

| 维度 | 现实约束 |
| --- | --- |
| 使用者 | 单机自托管的运维者、站长、外包开发者；平台内所有登录操作员**等权**，没有管理员角色 |
| 部署 | 单容器多进程，一个 AppHub 进程；可能跑在 2C4G 的云主机上 |
| 网络 | 可能没有外网（内网/离线部署），可能不配置模型 |
| 数据 | 应用由 Docker/Stack 承载，配置真源在 Gitea，访问由 NPM 代理 |

由此推出两条硬需求：**不配模型也必须可用**；**不能假设“管理员”存在**（凡是需要角色的设计都要显式说明）。

### 3.2 任务目录

助手的覆盖范围等于平台的功能面，不是“只有排障”。下表是首版任务目录，每一行都是可验收的用户任务。

| 域 | 用户怎么说 | 助手做什么 | 阶段 |
| --- | --- | --- | --- |
| 应用部署 | “帮我部署一个 WordPress”“有哪些可以装的”“这个模板要多少内存” | 检索模板与版本 → 说明必填项与资源需求 → 资源/端口/编排预检 → 生成部署计划 → 确认后安装 → 跟踪进度 → 验证访问 | P1 预检，P2 安装 |
| 应用运行 | “这个应用打不开”“报 502”“特别慢”“一直重启” | 分层定位 → 收集证据 → 给结论与建议 → 人工修复指引或受控执行 → 复查 | P0 |
| 应用变更 | “改一下环境变量”“换端口”“升级到新版本” | 读现状与差异 → 影响与风险 → 确认 → 变更并重建 → 验证健康 | P2 |
| 应用访问 | “绑定域名”“开 HTTPS”“证书过期了”“限制访问” | 检查现网与目标一致性 → 联动方案（应用地址/网络/反代）→ 确认 → 执行 → 验证 DNS/TLS/可达 | P2 |
| 应用数据 | “怎么备份”“从备份恢复”“文件权限不对” | 说明覆盖范围与一致性限制 → 计划或执行 → 恢复前检查 → 结果核对 | P2 |
| 数据连接 | “数据库连不上”“连接串怎么写” | 读应用外部库配置（脱敏）→ 连通性测试 → 给出连接参数与排错点 | P1 只读，P2 写入 |
| 资源清理 | “磁盘快满了，哪些能安全清理” | 跨对象盘点（镜像、卷、日志、备份、构建缓存）→ 引用与归属检查 → 候选清单与影响 → 确认清理 → 释放量核对 | P0 盘点，P2 清理 |
| 平台运维 | “某个服务不正常”“平台变慢”“升级卡住了”“镜像拉不下来” | 服务状态与日志、资源占用、镜像源连通、升级状态 → 结论与处理路径 | P0 |
| 计划任务 | “定时备份怎么设”“任务为什么失败”“清理日志” | 任务与运行记录 → 失败原因 → 调整建议 → 受控修改 | P1 只读，P2 修改 |
| 配置仓库 | “改了配置没生效”“怎么回退” | 读文件与提交 → 差异 → 说明生效路径（重建/更新栈）→ 受控提交与回退 | P2 |
| 账号与设置 | “再加一个人”“SMTP 怎么填”“镜像加速怎么配” | 解释字段与影响 → 引导到对应设置页；账号与密钥类操作保持人工 | P0 引导 |
| 使用帮助 | “这个功能在哪”“这个参数什么意思”“有没有文档” | 知识检索 + 深链跳转；回答必须带出处 | P0 |

## 4. 端到端旅程

### 4.1 “帮我部署一个 WordPress”

```text
用户：帮我部署一个 WordPress
助手：确认版本与必要选项（表单：域名？内存？数据库？）
    → 预检：资源、端口、共享网络、模板必填项
    → 若条件不足：逐条说明缺什么、怎么补
    → 生成部署计划（步骤/影响/耗时）
    → 用户确认 → 执行安装 → 展示真实进度 → 完成后检查访问
```

### 4.2 “这个应用打不开”

```text
用户在应用详情：AI 排查（自动带应用标识）
    → 分层定位：外部可达 → 网关/反代 → 应用 → 容器 → 平台
    → 证据：状态、退出码、端口映射、反代目标、日志片段
    → 结论：已确认/可能/证据不足 + 缺失项
    → 建议：可执行（需确认）或人工步骤（带深链）
    → 用户操作后回到会话 → 复查 → 明确是否解决
```

### 4.3 “绑定域名并启用 HTTPS”

```text
用户：我想给这个应用绑定域名并启用 HTTPS
助手：检查应用监听端口、现有反代、DNS 解析、证书现状
    → 表单：域名、是否强制 HTTPS
    → 计划：反代创建 → 证书申请 → 应用地址更新（联动）
    → 确认 → 执行 → 验证 DNS/TLS/实际访问
    → 失败时说明是哪一步、当前状态、可选下一步
```

### 4.4 “磁盘快满了，哪些可以安全清理”

```text
用户：磁盘快满了
助手：分层盘点（平台数据根 / 镜像 / 卷 / 日志 / 备份 / 预拉缓存）
    → 引用与归属检查：哪些被运行中或已停用应用引用
    → 候选清单：可安全清理 / 需确认 / 禁止删除，附预计释放
    → 用户勾选 → 确认 → 清理 → 核对实际释放量
    → 说明：容器视角与宿主视角的差异（读不到的部分明确标注）
```

## 5. 交互形态

- **不是纯聊天**：对话负责意图与解释，结构化卡片负责事实与决策。
- 会话区固定显示目标（应用 / 平台 / 任务）与模式（只读 / 可执行）。
- 卡片类型：目标卡、证据卡、结论卡、步骤卡、表单卡、确认卡、结果卡、知识卡。
- 证据卡可跳转到既有页面；确认卡列出影响与风险；结果卡只给三种状态。
- 事件：`state` / `text` / `tool` / `evidence` / `proposal` / `error`，通过服务端 SSE 推送，前端只信服务端状态。

## 6. 能力边界

| 等级 | 含义 | 例子 |
| --- | --- | --- |
| 只读 | 无业务写副作用，直接执行 | 状态、日志、配置读取、盘点、知识检索 |
| 确认执行 | 说明影响后由用户确认 | 安装、启停、配置变更、域名/证书、清理、备份/恢复 |
| 人工 | AI 只解释与跳转 | 账号与密钥、控制面重启、主机授权准备、私钥上传 |
| 永不开放 | 任何情况下都不提供 | 任意 Shell/Exec、通用 SQL、明文凭证、任意 URL 抓取、任意文件路径 |

补充约束：

- 不通过自定义任务、预设命令、SSH 准备等既有入口间接绕过上述边界。
- 凭证明文与密码重置只走人工界面。
- 停用的应用可能仍保留数据，清理前必须核对归属与引用。

## 7. 非功能需求

| 类别 | 要求 |
| --- | --- |
| 时延 | 入口首屏 < 2s；首个确定性结论 < 5s（不含模型） |
| 隔离 | AI 进程被 kill / OOM / 升级，控制台其余功能不受影响 |
| 并发 | 多会话并行诊断不阻塞控制台接口 |
| 截断 | 日志与配置按预算截断并标记，不把截断当完整 |
| 审计 | 每次工具调用可追溯到操作员、会话、目标、结果等级 |
| 保留 | 会话默认 30 天；审计 90 天；可配置 |
| 可移植 | 不依赖外网；不新增对外端口；沿用现有登录态 |

## 8. 技术方案（支撑上述需求的最小形态）

```text
Console（原生页面：目标入口 / 对话 / 卡片 / 确认）
   │ /api/ai/*（现有登录态与网关）
AppHub：会话 · 批准 · 审计 · 确定性诊断引擎 · 工具执行（超时/范围/脱敏）
   ▲ 内部接口（回环 + 内部令牌）
AI 进程（Pydantic AI）：意图理解、工具选择、解释
   │ 出站 HTTPS（可选）
模型供应商
```

三个关键选择：

1. **AI 独立进程**：AppHub 是单 worker、无内存隔离、远程调用无超时；内嵌会让 AI 的故障升级为全平台故障。
2. **工具统一经 AppHub 执行**：AI 进程不持任何平台凭据，不能直连 Docker、不读数据根；超时、脱敏、审计、范围校验集中在一层。工具清单按目标类型下发，模型不能自行扩大范围。
3. **确定性引擎产出事实，模型只解释**：满足“不配模型也可用”，也让结论可复现、可翻译、可审计。

## 9. 交付阶段

| 阶段 | 覆盖任务 | 不包含 |
| --- | --- | --- |
| **P0 可用闭环** | 入口与目标路由、使用帮助、平台只读诊断、应用只读诊断、资源盘点（只读）、人工路径与复查 | 任何写操作 |
| **P1 引导与预检** | 部署引导（表单 + 预检）、数据连接检查、任务只读、参数解释 | 安装执行 |
| **P2 受控执行** | 安装、启停重启、配置变更、域名与证书、备份恢复、清理、任务修改 | 控制面重启、账号密钥 |
| **P3 覆盖与收口** | 其余任务补齐、旧 AI 入口下线、度量与回归 | 通用终端类能力 |

每个阶段的验收都必须包含：无模型路径、模型失败路径、证据不足路径、人工路径、越权目标、脱敏有效性、并发隔离。

## 10. 度量

| 指标 | 含义 |
| --- | --- |
| 首轮命中率 | 用户第一次描述即进入正确任务的比例 |
| 免菜单完成率 | 全程未点击侧边栏即完成任务的会话比例 |
| 定位效率 | 从发起到达成“定位到层 + 对象”的耗时 |
| 人工转交率 | 因能力未开放而转到人工页面的比例（用于排优先级） |
| 确认合规率 | 写操作中经确认且参数未被篡改的比例（应为 100%） |
| 结果明确率 | 结束时能给出“达成/未达成/无法确认”的会话比例 |

## 11. 与现有实现的对接点

| 对接点 | 现状 |
| --- | --- |
| 进程编排 | supervisord 已管理 8 个 program，支持单 program 重启与新增长驻进程 |

## 12. 待确认（功能级）

1. 首版任务目录是否需要包含“部署执行”（而不只是预检）——决定 P1 是否提前到 P0。
2. “查资料”是否只限镜像内文档，还是需要覆盖在线文档/社区。
3. 资源清理是否需要跨应用批量候选清单（如一次列出所有可删镜像与卷）。
4. 是否需要周期性主动巡检（每天自动跑一遍并出摘要），还是只响应式。
5. 人工操作后“回到会话复查”是否作为首版必需能力。
